# sales-data-pipeline

Небольшой конвейер данных на **Python + SQL**: собирает продажи из трёх разных
источников в один PostgreSQL, сверяет целостность, считает аналитику и выгружает
отчёт. Работает полностью офлайн на ноутбуке.

Данные синтетические (магазин автомагнитол): товары, комплекты, заказы, клиенты.
Боевых данных и секретов в репозитории нет.

## Поток данных

```
Источники                         Загрузка            База (PostgreSQL)      Аналитика        Отчёт
─────────────────────────────     ──────────          ─────────────────      ─────────        ─────
CRM-выгрузка (JSON)        ┐                           products / kits
Прайс менеджера (CSV)      ├──►  pipeline.load  ──►    kit_items / customers ──► sql/*.sql  ──► report.xlsx
Курсы ЦБ (XML API+кэш)     ┘      (upsert,              orders / order_items      (6 запросов)   + сводка
                                  журнал etl_runs)      fx_rates / etl_runs
                                       │
                                       └──►  pipeline.check  (сверка «было·дошло·выпало» + качество)
```

Три источника объединяются по естественным ключам: JSON даёт заказы и каталог,
CSV обновляет цены тех же товаров (по `sku`), API ЦБ добавляет курсы (в отчёте
выручка переводится в USD по последнему курсу).

## База в Docker одной командой

```bash
docker run -d --name sales-pipeline-db \
  -e POSTGRES_USER=pipeline -e POSTGRES_PASSWORD=pipeline -e POSTGRES_DB=sales_pipeline \
  -p 5433:5432 postgres:16
```

Строка подключения под эту базу (кладётся в `.env`):
`postgresql+psycopg://pipeline:pipeline@localhost:5433/sales_pipeline`.
Свой PostgreSQL тоже подойдёт — нужна пустая база и `DATABASE_URL` в `.env`.

## Запуск за 4 команды

```bash
pip install -r requirements.txt            # зависимости
cp .env.example .env                        # впишите свой DATABASE_URL
alembic upgrade head                        # 1) схема и миграции
python -m pipeline.load                     # 2) загрузка трёх источников
python -m pipeline.check                    # 3) сверка и проверки качества
python -m pipeline.report                   # 4) report.xlsx + сводка в консоль
```

Проверка: `pytest` (тесты зелёные), `ruff check .` (без ошибок).
Прайс-CSV при необходимости пересобирается: `python scripts/make_price_csv.py`.

## Что внутри

- **Схема** (`pipeline/models.py`, миграции `alembic/versions/`): `products`,
  `kits`, `kit_items`, `customers`, `orders`, `order_items`, `fx_rates`, `etl_runs`.
  Миграция `0001` создаёт схему, `0002` — написана руками: добавляет
  `customers.phone_normalized` и заполняет существующие строки одним `UPDATE`.
- **ETL** (`pipeline/load.py`): идемпотентная загрузка через `INSERT … ON CONFLICT
  DO UPDATE`. Каждый источник пишет строку в `etl_runs` (пришло / вставлено /
  обновлено / отброшено + причина).
- **Сверка** (`pipeline/check.py`): по каждой таблице «было в источнике · дошло ·
  выпало» и проверки качества — дубли клиентов по телефону, заказы без клиента,
  пустые телефоны.
- **Аналитика** (`sql/`): 6 запросов, каждый с комментарием «какой вопрос бизнеса
  решает»: выручка по месяцам (нарастающий итог), RFM через `NTILE`, продажи
  складских позиций с раскрытием комплектов, на сколько хватит остатка,
  повторные покупки, топ-10 за 90 дней.
- **Отчёт** (`pipeline/report.py`): `report.xlsx` — лист на запрос, русские
  заголовки; плюс сводка в консоль.

## Решения и почему так

- **Upsert по естественному ключу** (`sku`, `kit_code`, `source_order_id`,
  телефон, пара `char_code+date`), а не по автоинкременту. Так повторная загрузка
  не плодит дубли, а источник остаётся источником правды — это делает ETL
  безопасным для повторного и частичного запуска.
- **Журнал загрузок `etl_runs`.** Без него «данные просто появились»; с ним видно,
  сколько пришло и сколько выпало и почему — это первое, что спрашивают, когда
  цифры в отчёте расходятся с ожиданием.
- **Комплекты раскрываются в составе именно в SQL.** В заказах лежат артикулы
  комплектов (`kit-NN`), а склад считается по позициям. Без разворота
  `kit_items` половина расхода «не видна» — склад покажет остаток, которого нет.
  Разворот в запросе, а не на загрузке, оставляет заказ как есть (что продали —
  то и лежит) и считает склад в момент вопроса.
- **Сырой SQL вместо ORM в аналитике.** Оконные функции (`SUM … OVER`, `NTILE`),
  `FILTER`, разворот комплектов читаются и правятся аналитиком прямо в `.sql`, а в
  ORM это превратилось бы в нечитаемую конструкцию. ORM (SQLAlchemy) используется
  там, где он силён — модели, миграции и запись в ETL.
- **Внешний API с офлайн-кэшем.** Курсы ЦБ берутся онлайн, при успехе кэш
  обновляется; без сети — читаются из последнего кэша. Загрузка не падает из-за
  отсутствия интернета, что важно для надёжного ежедневного запуска.
- **Нормализация телефона — отдельной миграцией с заполнением.** Показывает
  рабочий приём: добавить поле в таблицу с данными и привести старые строки одним
  `UPDATE` тем же правилом, что применяет ETL к новым.
